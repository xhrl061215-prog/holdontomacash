# Deploying BudgetTracker for real users

Two things have to change for the app to outlive a sandbox:

1. **The database** must be hosted, not a local directory.
2. **Sessions** must persist, so logging in still works after a restart or
   redeploy.

Both are code-complete. What remains needs accounts under your own name, which is
why the steps below are yours to run — I cannot create accounts as you, and you
should not paste credentials into chat.

Total time: about 20 minutes. Everything is free tier.

---

## Step 1 — Create the database (Supabase, ~8 min)

1. Go to **supabase.com** → sign in with GitHub or email → **New project**.
2. Name it `budget-tracker`. Choose a region near your users (Seoul if that is
   most of them). Set a strong database password and save it in a password
   manager — you will not need it for the app, only for direct DB access.
3. Wait for provisioning (~2 min).

### Apply the schema

**Paste `supabase/SETUP.sql` once.** Left sidebar → **SQL Editor** → **New
query** → paste the whole file → **Run**. Expect `Success. No rows returned`.

That file is all eight migrations concatenated in the correct order, generated by
`npm run build:setup-sql` and verified by `npm run verify:setup-sql`. Do not paste
the migrations individually: ordering matters (`0003` and `0007` both define the
signup trigger and `0007` must win) and the bundle removes the chance of getting
it wrong. It runs inside a transaction, so a failure rolls back rather than
leaving a half-built database, and it is safe to run twice.

For a version of this written for someone who does not work with databases, see
[SETUP-GUIDE.md](SETUP-GUIDE.md).

### Turn on email login

**Authentication** → **Providers** → **Email**: enable it.

- Leave **Confirm email** ON for real users. They will receive a confirmation
  link, and the app tells them to check their inbox.
- Supabase's built-in mail is rate-limited to a handful per hour — fine for
  early users. For more, add an SMTP provider under **Project Settings** →
  **Authentication** → **SMTP**.

## Step 2 — Get the two keys (~1 min)

**Project Settings** → **API**. Copy:

- **Project URL** → `VITE_SUPABASE_URL`
- **anon public** key → `VITE_SUPABASE_ANON_KEY`

> The **anon** key is designed to sit in a browser. Row-level security denies
> every query until a policy matches the signed-in user, so it grants nothing on
> its own.
>
> **Never** use the **service_role** key here. It bypasses row-level security
> entirely — in a frontend build it would let anyone read every user's
> transactions. It belongs only in server-side secrets, and this app does not
> need it.

## Step 3 — Deploy the site (Vercel, ~6 min)

1. Push this repository to GitHub if it is not there already.
2. Go to **vercel.com** → sign in with GitHub → **Add New Project** → import the
   repository.
3. Vercel detects Vite automatically. Confirm:
   - Build command `npm run build`
   - Output directory `dist`
4. Under **Environment Variables**, add both keys from Step 2. Add them to
   **Production**, **Preview** and **Development**.
5. **Deploy.**

You get a permanent URL like `budget-tracker-xyz.vercel.app`. It stays up
independent of any sandbox, and every push redeploys it.

Netlify or Cloudflare Pages work identically — same build command, same output
directory, same two variables.

---

## Step 4 — Verify it before sharing it (~3 min)

Do these in order on the real URL:

1. **Sign up** with an email you can read. Confirm via the emailed link.
2. Complete onboarding: study country, local currency, home currency, budget.
3. **Add a transaction.**
4. **Log out, then log back in.** Your transaction is still there.
5. **Close the tab entirely, reopen the URL.** You are still signed in — this is
   the part the preview backend could not do.
6. **Open it on your phone.** Same account, same data.
7. Sign up a **second** account and confirm it sees none of the first account's
   transactions.

Step 7 matters most. Isolation is enforced by Postgres row-level security rather
than by application code, and `npm run verify:overview-fn` asserts it cannot be
bypassed even through the aggregation function — but verify it yourself on the
real deployment.

## What changes, and what does not

| | Preview (sandbox) | Hosted |
|---|---|---|
| Database | PGlite in a local directory | Supabase Postgres |
| Survives restart | No | Yes |
| Sessions | in server memory | refresh tokens, persisted |
| Stay logged in after redeploy | No | Yes |
| URL | dies with the sandbox | permanent |
| Isolation | RLS, same policies | RLS, same policies |
| Money arithmetic | SQL numeric | SQL numeric |

The app selects its backend from configuration: with both variables set it uses
Supabase, without them the preview API. No code edit switches it, so the hosted
path cannot drift from the one the tests cover.

## Currency rates in the hosted deployment

Conversion needs a server-side fetch. In the hosted setup that runs as a Supabase
Edge Function (`backfill-rates`), invoked when the app loads.

**Until you deploy that function, new transactions save with their conversion
pending** — the amount, currency and date are all stored exactly, and the
converted figure fills in once rates are available. Nothing is lost or guessed;
totals exclude pending rows and the UI says so rather than showing a wrong total.

Deploy it when convenient:

```bash
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase functions deploy backfill-rates
```

## Costs

Free tier covers early use: Supabase gives 500 MB of database and 50,000 monthly
active users; Vercel's hobby tier covers a personal project's bandwidth. A budget
tracker's rows are tiny — thousands of transactions are a few megabytes.

Supabase pauses a free project after **7 days with no requests**. It resumes when
next visited, and no data is lost, but if the app will sit idle for long stretches
either visit it occasionally or move to their paid tier.

## If something goes wrong

**"Invalid API key"** — a variable is missing or has a stray space. Check both in
Vercel, then redeploy (env changes need a fresh build).

**Sign-up succeeds but nothing arrives** — confirmation email is on and either
went to spam or hit the built-in rate limit. Check
**Authentication → Users**: the account exists but is unconfirmed. Configure SMTP
for volume.

**"relation does not exist"** — a migration did not run. Re-apply the numbered
files in order.

**Categories look duplicated** — a migration ran out of order, so both signup
triggers exist. Re-run `0007_seed_brief_lists.sql`; it is written to be safely
re-runnable and `npm run verify:seed` proves that.

**Overview is empty but transactions exist** — `0008` did not apply. Re-run it.
